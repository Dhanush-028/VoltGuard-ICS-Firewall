# VoltGuard - C++ Modbus/TCP Parser

This closes a real gap against the project PDF's literal Week 1 line:
*"Build a C++ script to parse mock Modbus/TCP traffic. Create a script
generating normal and malicious industrial commands."* The original Week 1
build did this in Python (`protocol.py`) - functionally correct, but not
the language the spec actually named. This is the C++ version.

## What it proves

Not just "this C++ code parses frames it made itself" - it was checked
against the **already-validated Python implementation**:

1. A frame was generated by the real `protocol.py` on the Python side for
   known inputs (transaction_id=1, unit_id=1, register_addr=1, rpm=2800).
2. That exact hex (`000100000006010600010af0`) is hardcoded into this C++
   program's self-test as a parity check.
3. The C++ parser decodes it and gets back **exactly** the same field
   values Python produced.
4. It was also handed a completely fresh, independently-generated Python
   frame for the 50,000 RPM problem-statement scenario via `--hex`, and
   decoded it correctly.

That's the actual bar for "the C++ side really understands the wire
format" - agreement with an independent implementation, not just internal
self-consistency.

## Standard library only - no Qt, no CMake needed

Deliberately kept to plain C++17 + `<random>`, `<sstream>`, etc. Nothing
Qt-specific, no build system beyond a single g++ command, since this is a
protocol-parsing script, not a GUI app.

## Building on your Windows machine

You already have a MinGW g++ compiler installed from the Qt Creator setup
(used for `qt_dashboard`), so no new install needed. Two ways to compile:

**Option A - Qt Creator's terminal (easiest, no PATH setup):**
1. In Qt Creator: **Tools -> External -> ... -> ... ** or simpler, just
   open a normal PowerShell and run g++ using its full path:
   ```
   C:\Qt\Tools\mingw1310_64\bin\g++.exe -std=c++17 -O2 modbus_parser.cpp -o modbus_parser.exe
   ```

**Option B - if you add MinGW to PATH:**
```
g++ -std=c++17 -O2 modbus_parser.cpp -o modbus_parser.exe
```

## Running it

**Self-test (round-trip generation/parsing + parity check + malformed-frame
handling):**
```
modbus_parser.exe
```
Expect to see `--- ALL CHECKS PASSED ---` at the end.

**Decode a specific hex payload (this is the literal "parsing audit" the
project's mid-project review asks for - prove the engine accurately reads
Modbus hexadecimal payloads):**
```
modbus_parser.exe --hex 000100000006010600010af0
```
Feed it any hex frame - one you generated with `main_sim.py`/`network_demo.py`
on the Python side, or one you make up by hand - and it'll decode the
transaction ID, unit ID, function code, register address, and commanded
RPM.

## Scope note

This is a standalone parser/generator script, matching exactly what the
PDF's Week 1 line asks for - it does not replace `protocol.py` in the
running network bridge (`gateway.py`), which still uses the Python
version. Wiring this C++ parser into the actual live gateway (instead of
just proving it reads the same wire format correctly) would be a Week 3/4
"port the hot path to a faster language" task, same category as the
planned Rust decision engine port - worth doing together if you want the
whole pipeline off Python eventually, but out of scope for what the PDF
asks for at this stage.
